# Unit 3: Unit 3: Design, Architecture, Process Models

## Golden Points
1. Coupling is dependency between modules, cohesion is how related things inside a module are. Aim: low coupling, high cohesion
2. Coupling types worst to best: content, common, control, stamp, data. Cohesion best to worst: functional, sequential, communicational, procedural, temporal, logical, coincidental
3. Structure chart is derived from a DFD by transform or transaction analysis
4. Architecture views: logical, process, development, physical, plus scenarios (4+1)
5. Styles: layered, client server, pipe and filter, MVC, microservices, event driven, repository
6. Waterfall is sequential, needs fixed requirements, no going back. Good for small clear projects
7. Prototyping and evolutionary models build a working sample, refine with feedback
8. Incremental model delivers working parts one by one. V model pairs each phase with a test level
9. Spiral model is risk driven: planning, risk analysis, engineering, evaluation in loops
10. RAD is fast, component based, 60 to 90 days. RUP has inception, elaboration, construction, transition

## Exam answers / numericals (as shown in video)

### Scene 2: Low coupling + High cohesion = good design
    ## Coupling vs Cohesion
    Coupling: interdependence between modules
    Cohesion: strength of relation inside a module
    ## Design principle
    Low coupling: change in one module does not spread
    High cohesion: module does one job well
    ! Good design = low coupling and high cohesion
    ## Impact on quality
    Better maintainability, testability, reusability

### Scene 3: DFD > identify transform > structure chart hierarchy
    ## Structure chart from DFD
    1 Draw DFD
    2 Find type: transform or transaction flow
    3 Mark afferent, central transform, efferent branches
    4 Create main module on top
    5 Add input, process, output modules below
    ! Structure chart = module hierarchy with data and control flow

### Scene 4: Architecture = blueprint. 4+1 views
    ## Importance
    Blueprint for developers and stakeholders
    Drives quality: performance, security, scalability
    Allows early analysis and reuse
    ## Views (4+1)
    Logical, Process, Development, Physical
    Plus Scenarios linking them
    ! Different stakeholders need different views

### Scene 5: Styles: Layered, Client server, Pipe filter, MVC, Microservices
    ## Architecture styles
    Layered, client server, pipe and filter
    MVC, microservices, event driven, repository
    ## ADR template components
    Title: short name of decision
    Status: proposed, accepted, superseded
    Context: problem and forces
    Decision: what we chose and why
    Consequences: benefits and trade offs
    ! Record every important decision

### Scene 6: Pattern = proven reusable solution to common design problem
    ## Design pattern
    Reusable solution to a recurring design problem
    ## Pattern based design
    1 Identify problem 2 Choose pattern 3 Apply and adapt
    ! Benefits: reuse, common vocabulary, proven quality

### Scene 7: Waterfall: phases ek baar, peeche wapas nahi
    ## Waterfall
    Linear sequential, each phase finishes before next
    ## Advantages
    Simple, easy to manage, good documentation
    ## Problems
    Real projects rarely follow it, requirements change
    Working software only at the end
    Customer sees product very late
    Risks and errors found late
    ! Best for small projects with clear fixed requirements

### Scene 8: Prototype > Customer feedback > Refine > repeat
    ## Prototyping
    Working sample built early to clarify requirements
    Types: throwaway and evolutionary
    ## Advantages
    Unclear requirements become clear, high user involvement
    ## Disadvantages
    Poor design if prototype is kept, many iterations, scope creep
    ! Use when requirements are unclear

### Scene 9: Incremental: part by part. Each increment = working software
    ## Incremental model
    Requirements split into increments
    Each increment goes through design, code, test and is delivered
    ## Advantages
    Early working software, lower risk, easier changes
    ## Disadvantages
    Needs good planning and architecture, integration effort
    ! Example: messaging app, then calls, then status

### Scene 10: V model: har phase ka apna test level
    ## V model
    Each development phase is paired with a testing phase
    Requirements with acceptance, design with system
    Architecture with integration, module design with unit
    ## Pros and cons
    Test planning early, but rigid and no early prototype
    ! Left = verification, right = validation

### Scene 11: Spiral = Plan > Risk analysis > Engineer > Evaluate, loops
    ## Spiral model
    Risk driven, combines prototyping and waterfall
    Four quadrants in every loop
    ## Risk handling
    Risk analysis and prototype at every loop
    Stop or change plan if risk too high
    ## Pros / cons
    Best for large risky projects, but costly, needs risk expertise
    ! Spiral = risk handling model

### Scene 12: RAD: 60 to 90 days, reuse. RUP: 4 phases
    ## RAD
    Very short cycle using reusable components and parallel teams
    Phases: business, data, process modelling, application generation, testing
    Needs skilled team, only for modular systems
    ## RUP
    Inception, elaboration, construction, transition
    Use case driven, architecture centric, iterative
    ! RAD = speed, RUP = disciplined iterative

### Scene 13: Problem dekho, model chuno (Omnitrix)
    ## Choosing a model
    Match the model to requirement clarity, risk, time
    ! Fixed and clear: Waterfall. Risky: Spiral. Changing: Agile
    ~ Trick: Clear-W, Unclear-P, Risk-S, Test-V, Fast-RAD
