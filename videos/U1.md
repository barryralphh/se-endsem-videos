# Unit 1: Unit 1: Introduction, SDLC, Agile

## Golden Points
1. Software is programs plus data plus documents. It is engineered, not manufactured, and it does not wear out but it deteriorates with changes
2. Software crisis means projects late, over budget, poor quality, hard to maintain. Cause: size and complexity grew faster than methods
3. SDLC phases: requirements analysis, design, coding, testing, maintenance
4. Structured approach is function oriented using DFD. OOAD is object oriented using classes and UML
5. Traditional models are plan driven and follow phases. Agile is iterative, customer collaborative, welcomes change
6. Scrum: 3 roles, 3 artifacts, 5 events, sprint of 2 to 4 weeks
7. XP practices: pair programming, TDD, small releases, refactoring, continuous integration
8. FDD five steps: develop overall model, build feature list, plan by feature, design by feature, build by feature
9. Domain object modelling in FDD gives a shared class model that features are built on
10. Crystal is a family of methods by team size and criticality. DevOps joins development and operations with CI and CD

## Exam answers / numericals (as shown in video)

### Scene 2: Software = programs + data + documents. Engineered, not manufactured
    ## Software
    Programs + data + documentation
    ## Applications
    System software, application software
    Embedded and real time software
    Web apps, AI and scientific software
    ! Software does not wear out but deteriorates due to changes
    ## Evolution
    Assembly > structured > object oriented > web / cloud / AI

### Scene 3: Crisis = late + costly + buggy. Keywords: cost, quality, time
    ## Problem
    Projects run late and over budget
    Software is unreliable and hard to maintain
    ## Causes
    Vague and changing requirements
    Growing size and complexity
    Poor planning, estimation, communication
    Lack of methods and inadequate testing
    ## Impact
    Timeline: delay. Budget: overrun. Quality: more defects
    ! Solution: software engineering, a disciplined approach

### Scene 4: SDLC: Requirements > Design > Coding > Testing > Maintenance
    ## SDLC phases
    1 Requirements analysis: gather and specify needs, SRS
    2 Design: architecture, modules, data design
    3 Coding: implement design in a language
    4 Testing: find and fix defects
    5 Maintenance: corrective, adaptive, perfective
    ! Each phase produces a document that feeds the next

### Scene 5: Structured = functions + DFD. OOAD = objects + UML
    ## Structured
    Function oriented, top down decomposition
    DFD, data dictionary, structure chart
    ## OOAD
    Object oriented, classes and objects
    Encapsulation, inheritance, polymorphism, UML
    ! Function oriented design = functions, Object oriented design = objects

### Scene 6: Agile = chhote iterations + customer feedback + change welcome
    ## Agile manifesto
    Individuals and interactions over processes
    Working software over comprehensive documentation
    Customer collaboration over contract negotiation
    Responding to change over following a plan
    ! Small increments, delivered often

### Scene 7: Traditional = PLAN. Agile = ADAPT
    ## Agile vs Traditional
    Traditional: plan driven, sequential, rigid
    Agile: adaptive, iterative, flexible
    ! Customer involvement: low in traditional, continuous in agile
    ! Delivery: one big bang vs small increments
    ~ Trick: Plan vs Adapt

### Scene 8: Scrum: Backlog > Sprint > Daily scrum > Review > Retro
    ## Scrum
    Roles: Product Owner, Scrum Master, Dev Team
    Artifacts: product backlog, sprint backlog, increment
    Events: sprint, planning, daily scrum, review, retrospective
    ! Sprint = fixed time box of 2 to 4 weeks

### Scene 9: XP: pair programming + TDD + small releases + CI
    ## XP practices
    Pair programming, TDD, refactoring
    Small releases, continuous integration
    Simple design, collective ownership
    On site customer, 40 hour week
    ! Values: communication, simplicity, feedback, courage

### Scene 10: FDD: Model > Feature list > Plan > Design > Build
    ## Domain object modelling in FDD
    Class model of the business domain made with domain experts
    Shared understanding, features hang on the model
    ## Contribution
    Consistent design, less rework, easy progress tracking
    ## Challenges
    Needs domain experts, upfront time
    Large domains make the model complex, hard to keep updated
    ! FDD = feature centred, model first

### Scene 11: Crystal = by team size. DevOps = Dev + Ops, CI/CD
    ## Crystal
    Family of agile methods chosen by team size and criticality
    Focus on people, communication, frequent delivery
    ## DevOps
    Culture joining development and operations
    CI, CD, automation, monitoring
    ! Result: faster, more reliable releases
