# Unit 2: Unit 2: Requirements and Modelling

## Golden Points
1. Requirements engineering steps: inception, elicitation, analysis, specification, validation, management
2. Functional requirements say what the system does. Non functional say how well: performance, security, usability. Domain requirements come from the application domain
3. Elicitation techniques: interview, questionnaire, brainstorming, JAD, scenario, mind map
4. Use case diagram has actors, use cases, system boundary, and include and extend relations
5. SRS is the contract between customer and developer. IEEE 830 has introduction, overall description, specific requirements
6. Good SRS is correct, unambiguous, complete, consistent, verifiable, modifiable, traceable
7. ER diagram shows static view: entities, attributes, relationships, cardinality
8. DFD shows functional view: process, data store, external entity, data flow. Context diagram is level 0
9. State transition diagram shows dynamic view: states, events, transitions
10. Data dictionary defines every data item. Process specs use structured English, decision table or decision tree

## Exam answers / numericals (as shown in video)

### Scene 2: RE steps: Inception > Elicit > Analyse > Specify > Validate > Manage
    ## Importance of RE
    Wrong requirements give the wrong product
    Errors found late cost 10 to 100 times more
    Gives a base for design, testing, estimation
    ## Steps
    1 Inception 2 Elicitation 3 Analysis and negotiation
    4 Specification (SRS) 5 Validation 6 Management
    ! Requirements are the foundation of the SDLC

### Scene 3: Functional = KYA. Non functional = KITNA ACHHA. Domain = field ke rules
    ## Functional
    What the system should do
    ## Non functional
    Performance, security, reliability, usability, portability
    ## Domain
    Rules of application area, e.g. banking law
    ! Example: withdraw cash (functional), done within 5 seconds (non functional)

### Scene 4: Interview, Questionnaire, Brainstorming, JAD, Scenario, Mind map
    ## Any three
    Interview: talk to stakeholders, structured or open
    Questionnaire: written questions to many users, cheap
    Brainstorming: group generates ideas, no criticism
    JAD: customers and developers in a facilitated workshop
    ! Choose by users, time and detail needed

### Scene 5: Use case diagram: Actor + Use case + System boundary + include/extend
    ## Components
    Actor: external user or system
    Use case: one functionality, an oval
    System boundary: rectangle around use cases
    Relations: association, include, extend, generalisation
    ## Scenario (Withdraw)
    Main: insert card, enter PIN, choose amount, take cash
    Alternate: wrong PIN, low balance
    ! Use case diagram = functional view for users

### Scene 6: SRS = contract + base for design and testing
    ## Importance of SRS
    Agreement between customer and supplier
    Basis for design, testing and estimation
    Reduces development effort and disputes
    Helps maintenance and transfer to new users
    ## IEEE 830 key components
    Introduction, overall description, specific requirements
    ! Good SRS: unambiguous, complete, consistent, verifiable

### Scene 7: Requirements change hongi: track karo, trace karo
    ## Requirements management
    Controls changing requirements
    Version control, traceability matrix, change control
    ## Human oriented SE
    Design around users and their tasks
    Usability, user involvement, good user experience
    ! Traceability links requirement to design, code and test

### Scene 8: Static = ER, Functional = DFD, Dynamic = State diagram
    ## Role of modelling
    Simplifies complex requirements, helps communication
    Finds missing and conflicting requirements
    ## Views
    Static: ER diagram
    Functional: Data flow diagram
    Dynamic: State transition diagram
    ! UML is the standard for object oriented analysis

### Scene 9: ER: Entity (box), Relationship (diamond), Attribute (oval)
    ## ER diagram
    Student(RollNo, Name, Dept)
    Professor(EmpId, Name)
    Course(CourseId, Title, Credits)
    Department(DeptId, Name)
    ## Relationships
    Student M:N Course (enrolls)
    Professor 1:N Course (teaches)
    Department 1:N Professor (has)
    ## Data dictionary
    RollNo = integer, unique, primary key
    ! Static view of the data

### Scene 10: DFD: Process (circle), Entity (box), Data store, Data flow arrows
    ## Level 0 (context)
    User > [Railway Reservation System] > User
    ## Level 1 processes
    1 Register: name, email, password to User DB
    2 Login: check credentials from User DB
    3 Search: origin, destination, date, class to Train DB
    4 Display trains: number, time, duration, seats
    5 Select train
    ! Every process needs input and output flows

### Scene 11: State diagram: states + events + transitions
    ## ATM states
    Idle > Card inserted (insert card)
    Card inserted > Authenticated (PIN ok)
    Card inserted > Blocked (3 wrong PINs)
    Authenticated > Processing (choose transaction)
    Processing > Idle (card ejected)
    ## Shopping cart
    Empty, Has items, Payment pending, Order placed, Cancelled
    ! State diagram shows behaviour over time

### Scene 12: Data dictionary: + and, [ | ] or, { } repeat, ( ) optional
    ## Data dictionary example
    Name = First + (Middle) + Last
    Order = OrderId + Date + {Item}
    ## Process spec (Structured English)
    IF amount > 1000
       discount = 10%
    ELSE discount = 0
    ! Techniques: structured English, decision table, decision tree
