# Unit 4: Unit 4: Software Testing

## Golden Points
1. Error is human mistake, fault or bug is the defect in code, failure is wrong behaviour when the program runs
2. Verification asks are we building the product right, validation asks are we building the right product
3. Levels of testing: unit, integration, system, acceptance. Integration can be big bang, top down with stubs, bottom up with drivers, or sandwich
4. White box looks inside the code: statement, branch, condition and path coverage
5. Cyclomatic complexity V of G = E minus N plus 2 = P plus 1 = number of regions. It equals the number of independent paths
6. Basis path steps: draw flow graph, find V of G, list independent paths, write one test case per path
7. BVA tests min, min plus, nominal, max minus, max. Single fault gives 4n plus 1, robust gives 6n plus 1, worst case gives 5 to the power n
8. Equivalence class testing: one test from each valid and invalid class
9. Decision table: conditions on top, actions below, every column is a rule and a test case
10. Cause effect graph converts causes and effects to a decision table. State table testing checks every state and event pair
11. Agile testing is continuous. TDD cycle is red, green, refactor

## Exam answers / numericals (as shown in video)

### Scene 2: Error (insaan ki galti) > Fault (code mein bug) > Failure (run pe galat output)
    ## Definitions
    Error: mistake made by a developer
    Fault (bug, defect): incorrect step in the code caused by an error
    Failure: system behaves differently from expected when fault is executed
    ! Error > Fault > Failure
    ~ A fault may never cause a failure if that line never runs

### Scene 3: Verification: product SAHI bana? Validation: SAHI product bana?
    ## Q: V vs V
    ! Verification = are we building the product right
    ! Validation = are we building the right product
    ## Do both use test case design and strategies?
    Validation: YES. Black box and white box test case design, plus unit, integration, system, acceptance strategies
    Verification: NO execution. Uses reviews, inspections, walkthroughs, checklists
    ~ V model: left arm verification, right arm validation

### Scene 4: Unit > Integration > System > Acceptance (Pichu > Pikachu > Raichu > Mega)
    ## Levels
    Unit: smallest part, module by module
    Integration: combine modules, find interface bugs
    System: complete software, functional and non functional
    Acceptance: customer decides to accept or reject
    ! Alpha = at developer site, Beta = at customer site

### Scene 5: Top down = STUBS, Bottom up = DRIVERS, Sandwich = dono
    ## Approaches
    Big bang: all modules together, hard to locate bugs
    Top down: test top first, stubs replace lower modules
    Bottom up: test lowest first, drivers call the modules
    Sandwich: top down + bottom up meet in the middle
    ## PYQ link: scheduling and integration testing
    Module delivery order decides integration order
    Late module means more stubs, delay in testing
    ! Critical path modules must be integrated and tested first

### Scene 6: System testing = recovery, security, stress, performance, usability + regression
    ## Alpha vs Beta
    Alpha: controlled, at developer site, by internal users
    Beta: real environment, at customer site, real users
    ! Regression test after EVERY change

### Scene 7: White box = code ke andar. Statement < Branch < Condition < Path
    ## Coverage types
    Statement: every line runs at least once
    Branch: every decision true and false
    Condition: every atomic condition true and false
    Path: every independent route
    ## Example
    Tests: a=5 (true) and a=-5 (false)
    ! 2 tests give 100% statement and branch coverage
    ~ Static testing = review without running

### Scene 8: Flow graph > V(G) > Independent paths > Test cases
    ## Cyclomatic complexity V(G)
    V(G) = E - N + 2
    V(G) = P + 1
    V(G) = number of regions
    ! V(G) = number of independent paths = minimum tests
    ~ Higher V(G) means more complex, riskier code

### Scene 9: E = 8, N = 7 => V(G) = 3 independent paths
    ## Count
    Nodes N = 7
    Edges E = 8
    V(G) = E - N + 2 = 8 - 7 + 2 = 3
    Predicates: node 2, node 3 so P = 2
    V(G) = P + 1 = 3
    ## Independent paths
    P1: 1-2-7
    P2: 1-2-3-4-6-2-7
    P3: 1-2-3-5-6-2-7
    ## Test cases
    n = 0 covers P1, n = 2 covers P2, n = 1 covers P3
    ! V(G) = 3, three test cases

### Scene 10: Quadratic roots: E = 12, N = 10 => V(G) = 4 => 4 test cases
    ## V(G)
    N = 10, E = 12
    V(G) = 12 - 10 + 2 = 4
    P = 3 (a=0, d<0, d=0) so P + 1 = 4
    ## Independent paths
    P1: 1-2-3-10
    P2: 1-2-4-5-6-10
    P3: 1-2-4-5-7-8-10
    P4: 1-2-4-5-7-9-10
    ## Test cases (a,b,c)
    (0,5,5) Not quadratic
    (1,1,1) d=-3 Imaginary
    (1,2,1) d=0 Equal
    (1,5,1) d=21 Real
    ! 4 test cases

### Scene 11: BVA: min, min+, nom, max-, max.  4n+1, robust 6n+1, worst 5^n
    ## BVA a,b,c in [1,100], nom 50
    (1,50,50) Real  (2,50,50) Real
    (99,50,50) Imag  (100,50,50) Imag
    (50,1,50) Imag  (50,2,50) Imag
    (50,99,50) Imag  (50,100,50) Equal
    (50,50,1) Real  (50,50,2) Real
    (50,50,99) Imag  (50,50,100) Imag
    (50,50,50) Imag (nominal)
    ! 4n + 1 = 13 cases
    ## Robust adds
    0 and 101 for each variable: 6 more = 19 cases
    ~ Outputs: d = b2 - 4ac

### Scene 12: Domain ko classes mein todo, har class se ek test
    ## ECP steps
    1. Find input conditions
    2. Divide into valid and invalid classes
    3. Pick one value from each class
    ! 3 classes = 3 test cases
    ## Types
    Weak normal: one class at a time
    Strong normal: all combinations of valid classes
    Robust: also invalid classes

### Scene 13: Decision table: har column ek rule = ek test case
    ## Code (white box)
    2 if new: d += 15
    3 if not new and loyal: d += 10
    4 if not new and coupon: d += 20
    V(G) = 3 decisions + 1 = 4
    ## Branch coverage (3 tests)
    T1 new=Y: 15
    T2 new=N, loyal=Y, coupon=Y: 30
    T3 all N: 0
    ## Condition coverage adds
    T4 new=Y, coupon=Y: 15 (blocked)
    T5 loyal only: 10
    T6 coupon only: 20
    ! 6 tests cover all rules

### Scene 14: Cause effect > decision table. State table: har state x event ek test
    ## Cause effect graph steps
    1. List causes (inputs) and effects (outputs)
    2. Draw graph with AND, OR, NOT
    3. Convert to decision table
    4. Each column = test case
    ## State table testing
    Rows = states, columns = events, cell = next state
    ! Test every state and event pair

### Scene 15: TDD: Red (fail) > Green (pass) > Refactor > repeat
    ## Agile testing
    Testing done continuously inside every sprint
    Tester and developer work together
    Automated regression suite after every build
    ## TDD
    Write test first, it fails (Red)
    Write minimum code to pass (Green)
    Improve design without changing behaviour (Refactor)
    ! Benefit: fewer bugs, safe changes, living documentation
